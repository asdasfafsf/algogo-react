# 로컬 구현과 이슈 작업 절차

입력은 Linear 이슈 번호 또는 작업 설명이다. 검토·설계·기술 선택에 대한 대화만으로 구현을 시작하지 않는다. 실제 변경을 요청받으면 아래 절차로 로컬 구현·검증을 진행한다. Linear 쓰기는 [Linear 작업 범위](linear.md#작업-범위)에 따라 현재 요청에서 승인된 경우에만 수행한다.

## 1. 로컬 작업과 이슈 연결

- 요청한 결과와 범위를 먼저 확인한다. 대화에서 확정된 기술 선택은 유지하고, 검토 중인 선택을 확정된 변경으로 취급하지 않는다.
- 이슈 번호나 이슈 관리 요청이 있으면 [Linear 규칙](linear.md)을 읽고 해당 프론트 프로젝트의 이슈를 확인한다. 단순한 로컬 변경을 시작하기 위해 외부 이슈 조회·생성을 강제하지 않는다.
- 연결할 실제 이슈가 없으면 [Git 규칙](git.md)에 따라 detached 워크트리에서 구현·검증한다. 기존 이슈가 있으면 새 이슈 생성 승인 없이 그 이슈 번호의 브랜치를 사용한다. 연결 장애가 있어도 외부 시스템에 의존하지 않는 로컬 작업은 계속한다.
- 이슈 생성까지 승인되었으면 중복 확인 후 생성하며 같은 승인을 다시 묻지 않는다. 연결된 이슈의 상태 갱신도 승인 범위에 있을 때만 수행한다.

## 2. 별도 워크트리에서 구현

- 문서·설정을 포함한 변경 작업은 [Git 규칙](git.md)에 따라 별도 워크트리를 사용한다. 이미 지정된 워크트리가 있으면 이어서 사용한다. 새 작업은 기본적으로 `dev`에서 분기하되 사용자 지정 기준을 우선한다. 원래 작업 디렉토리에서 브랜치를 전환하지 않는다.
- 이슈가 연결된 브랜치명은 실제 이슈 번호를 사용한다. 이슈 연결 전에는 detached 워크트리의 변경으로 유지한다.
- 사용자가 위임을 요청했거나 적용 지침에서 요구한 경우, 지원되는 에이전트 도구로 위임하고 워크트리 경로·이슈 번호·제목·설명·작업 범위를 전달한다. 그 외에는 담당 에이전트가 워크트리에서 직접 수행한다.
- 코드를 구현하고 루트 AGENTS.md의 완료 기준에 따라 변경에 필요한 검증을 수행한다. 코드 변경에는 관련 테스트, 타입·런타임 변경에는 타입 검사와 빌드를 포함한다. 실패하면 원인을 확인하고 수정 후 재검증한다.
- 커밋이 요청 범위에 있고 실제 이슈가 연결되었을 때만 관련 파일을 `git add <파일>`로 스테이징한다. `git add -A`는 사용하지 않는다.
- 승인된 커밋은 `[ALGOGO-{번호}] {type}: {한글 설명}` 형식을 사용한다.

## 3. PR과 완료

- 로컬 구현·검증만 요청했다면 결과와 워크트리 경로를 보고하고 완료한다. 이슈 생성·PR·머지 승인을 자동으로 요구하지 않는다.
- 커밋·외부 반영이 요청됐지만 필요한 이슈 생성 승인이 없으면, 로컬 변경과 검증을 마친 뒤 제목·프로젝트·완료 조건이 있는 이슈 초안을 보여주고 필요한 승인만 요청한다. 확인이 필요한 정확한 규칙과 적용 이유를 링크한다.
- 요청에서 승인된 범위에 따라 기능 브랜치를 push하고 `dev` 대상 PR을 생성한다. 본문은 [Git 규칙](git.md)의 템플릿을 따른다.
- 이슈 상태 갱신도 승인된 경우 PR 생성 시 In Review로 바꾼다. 승인된 머지를 셀프 리뷰 직후 수행한다면 원래 규칙에 따라 생략할 수 있다.
- 리뷰와 테스트를 확인한 뒤 승인된 범위에서 squash merge하고 기능 브랜치를 삭제한다.
- 이슈 갱신이 승인되었고 실제 머지가 완료된 경우에만 Done으로 바꾸고 이슈 결과에 PR 링크를 기록한다.
- 구현·검증 결과와 미완료 항목을 한글로 보고한다.

대안을 비교하고 선택한 결정이 있으면 ADR 작성 필요성을 확인한다. 코드만으로 드러나지 않는 이유는 ADR에 기록한다.
