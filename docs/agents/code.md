# TypeScript / React 구현 기준

적용 대상: `src/**/*.{ts,tsx}`, 스타일, `tsconfig*.json`, `vite.config.ts`, `eslint.config.js`.

## 변경 범위와 타입

- 타입 안전성, API/소켓 계약, 사용자 동작을 우선한다. 요청에 필요한 범위만 수정하고 파일명·스타일 일괄 정리를 섞지 않는다.
- 현재 설정과 인접 코드를 확인한다. `strict`를 유지하며 `any`, 무분별한 단언, 검사 억제로 오류를 숨기지 않는다. 불확실한 외부 값은 `unknown`에서 검증하고 좁힌다.
- API 요청·응답과 상태 타입을 바꾸면 입력 → 변환 → 사용처를 추적한다. 확인하지 못한 백엔드 계약을 추정으로 변경하지 않는다.
- 추론이 명확하면 타입을 반복하지 않는다. 단언보다 타입 선언·타입 가드·`satisfies`를 우선한다. 유효한 상태는 유니온·판별 필드로 표현한다.
- 신규 상수 집합은 `as const` 객체를 기본으로 한다. 타입 전용 import는 `import type`을 사용한다.

## 컴포넌트와 상태

- 기존 `components/`, `layout/`, `page/`, `hook/`, `api/`, `zustand/` 역할을 따른다. 렌더링, 사용자 동작, 통신 책임을 구분하고 불필요한 계층을 추가하지 않는다.
- 컴포넌트는 PascalCase, 훅은 `use` 접두어, 변수·함수는 camelCase를 따른다. 기존 path alias와 import 관례를 유지한다. 백엔드의 상대경로 전용 규칙을 강제로 적용하지 않는다.
- 렌더 중 부수 효과를 만들지 않는다. effect의 의존성과 정리를 확인하고 React 훅 규칙을 지킨다. 리스너·소켓·타이머·에디터 리소스는 생성한 주체가 정리한다.
- Zustand 선택자는 안정적인 참조를 반환한다. 여러 필드를 새 객체/배열로 선택할 때는 개별 선택자 또는 `useShallow`를 사용한다.
- 서버 상태는 기존 TanStack Query/API 계층과 일관되게 다룬다. 로컬 UI 상태와 서버 캐시를 중복 관리하지 않는다. 인증 변경 시 캐시와 저장 상태의 수명도 확인한다.
- Router 경로·쿼리·뒤로 가기·인증 후 복귀 동작을 유지한다. Router나 Provider가 필요한 컴포넌트를 해당 컨텍스트 밖에 배치하지 않는다.

## 스타일과 접근성

- Tailwind 설정 위치와 현재 CSS를 확인한다. 테마·색상·글꼴·반응형 동작을 유지하고 버전 변경에 따른 클래스 문법을 확인한다.
- 의미에 맞는 요소와 접근 가능한 이름을 사용한다. 키보드 조작, 포커스 이동, 모달 닫기와 복귀 동작을 확인한다.
- 외부 HTML과 수식은 현재 신뢰 경계와 렌더링 계약을 확인한다. HTML 삽입 범위를 임의로 넓히지 않고, 내용 변경 시 재처리·중복 처리 여부도 검증한다.

## 비동기·설정

- `async/await`를 기본으로 하며 필요한 Promise 조합을 허용한다. 독립 조회는 병렬화하고 순서가 필요한 쓰기는 직렬화한다.
- 오류를 성공 응답이나 빈 결과로 바꿔 숨기지 않는다. 로딩·빈 결과·실패 상태를 구분하고 원인 파악에 필요한 맥락을 보존한다.
- 환경 설정은 Vite의 실제 주입 방식을 따른다. `VITE_` 변수는 브라우저에 노출되므로 비밀값을 넣지 않는다. 토큰·API 키·개인정보를 로그나 문서에 남기지 않는다.
- 의존성 변경 시 peer 범위·지원 런타임·잠금 파일을 확인한다. 에디터/워커/CDN 버전 불일치를 피하고 예외로 남긴 버전은 이유를 기록한다.

## 검증

- 버그는 가능하면 수정 전 재현과 수정 후 회귀 검증을 남긴다. 구현 문구나 mock 호출 횟수만이 아닌 관찰 가능한 동작을 검증한다.
- 상태·라우팅·의존성·타입·빌드 변경은 타입 검사와 빌드를 수행한다. 관련 정상·경계·실패 경로를 테스트하거나 실제 브라우저에서 확인한다.
- UI 변경은 관련 화면과 화면 크기를 확인한다. 테스트 스크립트가 없으면 있다고 가정하지 않고 적합한 검증 방법을 선택한다.
- 외부 API·인증·코드 실행은 mock 결과만으로 실서버 정상 동작을 단정하지 않는다. 검증에서 만든 데이터와 임시 파일을 정리한다.
- 기존 실패와 신규 회귀를 구분한다. 검증이 통과한 뒤에는 새 변경이나 실패 근거 없이 같은 검사를 반복하지 않는다.
